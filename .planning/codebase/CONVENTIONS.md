# Coding Conventions

**Analysis Date:** 2026-11-17

## Naming Patterns

**Files:**
- One public type per file, file name equals the type name: `src/SavegameBunker/Services/BackupService.cs` holds `BackupService`.
- View models end in `ViewModel`: `src/SavegameBunker/ViewModels/MainViewModel.cs`, `GameRowViewModel.cs`, `RestorePickerViewModel.cs`.
- Dialog views pair a `*.xaml` with a `*.xaml.cs` code-behind under `src/SavegameBunker/Views/` (`AddGameDialog`, `ChangeSaveFolderDialog`, `RestorePickerWindow`, `ScanWindow`).
- Dialog view models use the `*DialogViewModel` suffix (`AddGameDialogViewModel.cs`, `ChangeSaveFolderDialogViewModel.cs`).
- Interfaces use the `I` prefix in their own file: `src/SavegameBunker/Services/IDialogService.cs`.
- Result and record types live in `src/SavegameBunker/Models/` (`OperationResult.cs`, `BackupArchive.cs`, `SaveStatus.cs`).
- Test files are `<Subject>Tests.cs` in `tests/SavegameBunker.Tests/` (for example `BackupServiceTests.cs`, `PathResolverTests.cs`).

**Functions and methods:**
- PascalCase for all methods, including async ones: `Backup`, `ListBackups`, `RefreshAsync`, `ChangeSaveFolderAsync`.
- Async methods end in `Async` (`AddGameAsync`, `FindGamesAsync`, `RecomputeSpaceAdvisoryAsync`). Command handlers that are wired to `AsyncRelayCommand` follow the same rule.
- Predicates and checks read as questions or `Try` prefixes: `TryResolve` (`src/SavegameBunker/Services/PathResolver.cs`), `MatchesSearch`, `EnsureWritable`.

**Variables and fields:**
- Private instance fields: `_camelCase` with an underscore prefix, typically `readonly`: `_dialog`, `_backup`, `_gameActions`, `_selectedIds` in `src/SavegameBunker/ViewModels/MainViewModel.cs`.
- Locals and parameters: camelCase (`saveDir`, `pathError`, `backupRoot`).
- Constants and static readonly fields: PascalCase, not SCREAMING_CASE: `private const string PackUri` and `public const string DefaultFileName` in `src/SavegameBunker/Services/GameCatalog.cs`, `private static readonly JsonSerializerOptions ReadOptions` in the same file.
- Properties: PascalCase. Observable properties are generated by CommunityToolkit.Mvvm, so the backing field is written as a `[ObservableProperty]` private field and the public property is generated from it.

**Types:**
- Records are used for immutable value results and models: `public sealed record OperationResult(bool Success, string Message, bool Cancelled = false)` in `src/SavegameBunker/Models/OperationResult.cs`.
- Classes are `sealed` by default. The rule comes from `CLAUDE.md` and is applied to services, view models and test classes: `public sealed class BackupService`, `public sealed partial class MainViewModel`, `public sealed class BackupServiceTests`. 21 of the 50 hand-written source files declare a sealed type, so new concrete classes should be sealed and existing unsealed ones should not be changed without reason.
- Static helper classes use `public static class` (`src/SavegameBunker/Services/Strings.cs`) or `internal static class` for test-only helpers (`tests/SavegameBunker.Tests/TestFileSystem.cs`).

## Code Style

**Formatting:**
- No `.editorconfig`, `.prettierrc` or formatter config is committed. The effective style is what the existing files do.
- Allman braces: the opening brace of types, methods, and control blocks sits on its own line.
- Four-space indentation, no tabs.
- Single-line bodies are allowed for trivial members: `public static OperationResult Ok(string message) => new(true, message);` and `catch (UnauthorizedAccessException) { return SaveDirContent.Unreadable; }` in `src/SavegameBunker/Services/BackupService.cs`.
- Expression-bodied members are used for one-line forwarding methods (`public OperationResult Backup(...) => Backup(game, backupRoot, "", out _, progress);`).
- Nullable reference types are enabled in both projects (`<Nullable>enable</Nullable>`). Nullability is spelled out with `?` on every reference that may be null (`string? template`, `string? archivePath`).
- Implicit usings are on (`<ImplicitUsings>enable</ImplicitUsings>`), but files still list the `System.*` and `SavegameBunker.*` usings they need explicitly, sorted with `System` first. Do not remove those explicit usings during unrelated edits.

**Namespaces:**
- File-scoped namespaces everywhere in hand-written code: `namespace SavegameBunker.Services;`. Block-scoped namespaces are not used.
- Namespaces mirror folders: `SavegameBunker.Services`, `SavegameBunker.ViewModels`, `SavegameBunker.Models`. Tests use `SavegameBunker.Tests`.

**Linting:**
- No analyzer configuration or ruleset is committed. Code is kept warning-clean under the default SDK analyzers, with nullable warnings treated as things to fix rather than suppress.
- Suppressions are rare. `#pragma` and `#region` do not appear in hand-written sources.

## Import Organization

**Order (observed):**
1. `System` namespaces, alphabetical: `System.Collections.ObjectModel`, `System.Globalization`, `System.IO`, `System.Linq`, `System.Reflection`.
2. Third-party namespaces: `CommunityToolkit.Mvvm.ComponentModel`, `CommunityToolkit.Mvvm.Input`, `System.Windows`.
3. Project namespaces: `SavegameBunker.Models`, `SavegameBunker.Services`, `SavegameBunker.ViewModels`.

**Aliases:**
- When a type name collides with a project type, an alias is used: `using CommunityToolkitObservableObject = CommunityToolkit.Mvvm.ComponentModel.ObservableObject;` in `src/SavegameBunker/ViewModels/MainViewModel.cs`. Every view model in that namespace uses this alias to keep base class references unambiguous.

**Path aliases:** None. Projects are referenced by relative `ProjectReference`s only.

## Error Handling

The error contract is the most important convention in this codebase. It is stated in `CLAUDE.md` and enforced by the shape of every service.

**Services never throw across their boundary:**
- Operations return `OperationResult` (`src/SavegameBunker/Models/OperationResult.cs`) built with `OperationResult.Ok(message)`, `OperationResult.Fail(message)` or `OperationResult.Cancel(message)`.
- Each service wraps its body in `try` and maps known exceptions to plain messages. The mapping is per-exception-type, with a comment that explains why the case is expected:

```csharp
// src/SavegameBunker/Services/BackupService.cs
catch (IOException ex)
{
    // A locked archive — most commonly the zip open in another program — is the expected
    // failure here, so it gets its own plainly-worded message.
    return OperationResult.Fail(/* ... */);
}
catch (UnauthorizedAccessException ex)
{
    return OperationResult.Fail(
        $"The archive could not be deleted — access is denied: {archivePath} ({ex.Message})");
}
```

- Helper probes that answer a question return a status enum rather than throwing: `InspectSaveDir` returns `SaveDirContent.Unreadable` on `UnauthorizedAccessException` and `DirectoryNotFoundException` (`src/SavegameBunker/Services/BackupService.cs`).
- Out parameters are used for a second value next to the result: `Backup(..., out string? archivePath, ...)` and `PathResolver.TryResolve(..., out var saveDir, out var pathError)`. The `Try` pattern is the signal that failure is a normal return.
- Declining a confirmation is `OperationResult.Cancel(...)`, not a failure. Callers show only the status line for it.

**View models:**
- `MainViewModel.Report()` is the single sink: it pushes a message to `StatusMessage` and to a dialog. New commands report through it instead of calling dialogs directly.
- A command's task must not throw. An exception escaping an `AsyncRelayCommand` surfaces on the UI thread, so handlers convert every failure into an `OperationResult` first.

**Startup:**
- `App.OnStartup` (`src/SavegameBunker/App.xaml.cs`) is the only composition root. Its try/catch is a last resort for unexpected failures, not the normal route. Load errors go into the running window via `CatalogLoad`.

## Logging

**Framework:** None. The project forbids logging libraries (`CLAUDE.md`, two-dependency rule). There is no `ILogger`, no `Debug.WriteLine` pattern and no file logger in `src/`.

**Patterns:**
- User-visible diagnostics go through `IDialogService` and `OperationResult.Message`.
- Crash information is written by `src/SavegameBunker/Services/CrashReport.cs`, which is the only file-level diagnostic output.

## Comments

**When to Comment:**
- Comments explain *why*, not *what*. Most non-trivial decisions carry a rationale and often reference the spec: "a folder that exists and can be written to is the whole requirement" in `src/SavegameBunker/Services/BackupService.cs`.
- Comments state a constraint that a later editor might be tempted to break. Example from `src/SavegameBunker/ViewModels/MainViewModel.cs`: the `_selectedIds` store is keyed by `Game.Id` "not by row-object reference, because `RefreshAsync` ... construct brand-new `GameRowViewModel` instances."
- Comments are written in English, per `CLAUDE.md`, including in code, XAML and test files.

**XML documentation (`///`):**
- Required on public types and public methods. Use `<summary>`, `<remarks>`, `<param name="...">`, `<returns>`, `<see cref="..."/>` and `<para>` as in `src/SavegameBunker/Services/BackupService.cs`.
- Reference SPEC behaviour in the doc when the rule comes from it, for example "SPEC.md's *Backup destination* section".
- Private fields with non-obvious lifetimes also get `///` comments (see `_gamesSyncLock` and `_filterDebounce` in `src/SavegameBunker/ViewModels/MainViewModel.cs`).

**Inline:**
- Use `//` for short, local rationale. Multi-line rationale stays as a block of `//` lines of up to about 100 characters.

## Function Design

**Size:**
- Services split work into small private helpers rather than long methods (`BackupService` keeps `InspectSaveDir`, `EnsureWritable`, `ParseTakenAt` separate).
- Large view models are split by responsibility into collaborators, for example `CatalogSession` and `GameActions` used by `MainViewModel`.

**Parameters:**
- Services take explicit parameters, never a view model or dialog. Paths are resolved by the caller: `Backup(Game game, string backupRoot, ...)` takes an absolute, already-resolved root.
- Optional progress is passed as `IProgress<long>? progress = null`, so existing callers keep compiling.
- Overloads chain to the most complete signature (`Backup(game, root, progress)` forwards to the `out` overload).

**Return Values:**
- Operations return `OperationResult`. Queries return a value or a record (`CatalogLoad`, `BackupComparison`). Queries that can fail return `bool` with `out` or a result record, never an exception.

## Module Design

**Exports:**
- Types are `public` when used across the Services/ViewModels/Views boundary and `internal` for test helpers.
- Services have no WPF references and no static state beyond constants and static readonly options (`src/SavegameBunker/Services/GameCatalog.cs`).

**Dependencies:**
- Services are created directly as fields: `private readonly BackupService _backup = new();` in `src/SavegameBunker/ViewModels/MainViewModel.cs`. There is no DI container.
- Dialogs are injected through `IDialogService` in the view model's constructor. View models never call `MessageBox` or a folder picker directly.

**Barrel Files:** Not used. Each type is imported from its namespace.

## MVVM and WPF Conventions

- Base class: `CommunityToolkit.Mvvm.ComponentModel.ObservableObject`, aliased as shown above. Roughly 43 `[ObservableProperty]` fields and 27 `RelayCommand`-attributed or relay-command usages exist in `src/SavegameBunker/`.
- Commands: `AsyncRelayCommand` for anything that touches the filesystem, so `IsRunning` and `CanExecuteChanged` are handled by the toolkit. Synchronous commands use `RelayCommand`.
- Background work: `Task.Run` wraps filesystem work (about 35 call sites in `src/`). Services are synchronous; view models hop to the pool.
- Thread marshalling: `DialogService` (`src/SavegameBunker/Services/DialogService.cs`) marshals every dialog call onto the UI thread itself. View models do not use `Dispatcher` directly.
- `async void` appears once, as the WPF override `protected override async void OnStartup(StartupEventArgs e)` in `src/SavegameBunker/App.xaml.cs`. This is the framework-required exception; do not add other `async void` methods.
- Localised UI strings: all user-facing text comes from `src/SavegameBunker/Themes/Strings.en.xaml` through `Strings.Get(key)` or `Strings.Format(key, args)` (`src/SavegameBunker/Services/Strings.cs`). A missing key throws. Do not hard-code UI text in C# or XAML.

## Testing-Relevant Conventions

- Anything the view model needs from the outside is behind an interface (`IDialogService`) so tests can replace it. Services are concrete and tested directly against a temp folder.
- New behaviour must keep the destination rule: the backup code never inspects the volume type (see `CLAUDE.md`).
