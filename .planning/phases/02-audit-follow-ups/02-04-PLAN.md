Per-button block repeated ten times today (MainWindow.xaml toolbar, lines 36-161):
```xml
<ui:Button x:Name="ThemeToggleButton" Click="ThemeToggleButton_Click" DockPanel.Dock="Right"
        Style="{StaticResource ToolbarButton}" ToolTip="…" AutomationProperties.Name="…">
    <StackPanel Orientation="Vertical">
        <Viewbox Style="{StaticResource ToolbarGlyph}">
            <Path Style="{StaticResource ToolbarGlyphPath}" Data="{StaticResource Icon.Theme}"/>
        </Viewbox>
        <AccessText Text="{DynamicResource str_toolbar_toggleTheme}" Style="{StaticResource ToolbarButtonLabel}"/>
    </StackPanel>
</ui:Button>
```
Two labels are bound instead (`{Binding BackupSelectedLabel}`, `{Binding RestoreSelectedLabel}`).
Eight label keys carry an underscore (`_Add game`, `_Scan`, `_Refresh`, `_Open the games list`,
`_Change backup folder`, `_Back up selected`, `Res_tore selected`, `_Help`); `str_toolbar_toggleTheme`
("Switch theme") and `str_toolbar_backUpAllChanged` ("Back up all changed") do not.

Styles.xaml order matters: `ToolbarButton` (≈ line 301) is defined BEFORE `ToolbarGlyph`,
`ToolbarGlyphPath` and `ToolbarButtonLabel`; `OverflowMenuItem` (≈ line 112) BEFORE
`OverflowMenuGlyphPath`. A StaticResource naming a key defined further down the same dictionary
fails at runtime with a XamlParseException that `dotnet build` does not catch.

WPF-UI 4.3.0 Button template: its ContentPresenter carries
`ContentTemplate="{TemplateBinding ContentTemplate}"` and `RecognizesAccessKey="True"` (RESEARCH item 19).

Capture tooling from Plan 02-03 (see its SUMMARY for the exact invocations and any hand-taken
shots): `capture.ps1 -OutDir <dir> [-Shots <name,...>]` resets the demo data under
%TEMP%\SavegameBunkerDemo first, so every set starts from the same rows and archive state; it
drives the Release exe, so build Release before each capture.
